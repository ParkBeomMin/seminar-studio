# 세미나 코어

`_workspace/02_core.json` 하나가 요약·카드뉴스·인포그래픽·PPT **4종의 유일한 출처**다.
4종이 각자 전사본을 읽으면 서로 다른 사실을 말하게 되고, 그러면 어느 쪽이 맞는지
아무도 모른다. 그래서 판단은 여기서 **한 번만** 한다.

## 1. 스키마

```json
{
  "title": "세미나 제목",
  "speakers": [{ "name": "…", "affiliation": "…" }],
  "audience": "브리프에서 받은 대상 독자",
  "thesis": "이 세미나가 하려는 말 한 문장. 40자 내외",
  "sections": [
    { "id": "s1", "title": "…", "range": "00:04:12–00:21:40", "gist": "2~3문장" }
  ],
  "parts": [
    { "id": "part1", "title": "이 세션만의 제목", "kind": "talk | panel | qna",
      "range": "00:01:00–00:21:25", "speakers": ["…"],
      "thesis": "이 세션만의 한 문장", "sectionIds": ["s2","s3"] }
  ],
  "claims": [
    { "id": "c1", "section": "s1", "claim": "한 문장 주장",
      "support": "발표자가 댄 근거", "at": "00:07:31", "weight": 1 }
  ],
  "quotes": [
    { "id": "q1", "text": "전사본 그대로", "speaker": "…", "at": "00:12:05" }
  ],
  "numbers": [
    { "id": "n1", "label": "…", "value": 42, "unit": "%",
      "basis": "무엇 대비 언제 기준인지", "at": "00:33:10" }
  ],
  "takeaways": ["청중이 가져갈 실행 가능한 것 3~5개"],
  "qna": [{ "q": "…", "a": "…", "at": "01:22:40" }],
  "uncertain": ["복원 못 한 [?용어]와 그 맥락"],
  "assumptions": ["브리프에 없어서 내가 정한 것"],
  "confidence": "high | medium | low"
}
```

**`at` 없는 항목은 존재할 수 없다.** 타임코드를 못 다는 주장은 전사본에 근거가 없다는
뜻이고, 그건 배경지식으로 채운 것이다. 팩트체크가 잡기 전에 스스로 빼라.

## 1-1. `parts` — 한 녹음에 세션이 여럿일 때

세미나 녹음은 대개 한 세션이 아니다. 단독 발표 뒤에 패널이 붙거나, 발표자가 바뀐다.
**산출물은 파트 단위로 따로 만들어지므로 이 분할이 곧 산출물 개수를 정한다.**

- 파트를 나누는 기준은 **발표자 교체 또는 형식 전환**(발표→패널→Q&A)이다. 주제가 바뀌는
  것만으로는 나누지 않는다 — 그건 `sections`가 할 일이다
- 사회자 오프닝·세션 전환·부스 안내처럼 내용이 없는 구간은 **어느 파트에도 넣지 않는다.**
  `sectionIds`에서 빼면 된다
- 각 파트는 **자기만의 `thesis`**를 갖는다. 전체 `thesis`를 복사하지 마라 — 파트별 산출물의
  표지가 그 문장이 된다
- 세션이 하나뿐이면 `parts`에 항목 하나만 넣는다. 빈 배열로 두지 마라
- 같은 사람이 1부 발표자이고 2부 모더레이터일 수 있다. `speakers`는 **그 파트에서 실질적으로
  말한 사람** 기준으로 적는다

## 2. 판별 기준 — 무엇이 claim이 되는가

발표자가 **오래 말한 것**과 **강조한 것**은 다르다. 분량으로 뽑으면 곁가지가 올라온다.

| 신호 | 가중치 |
|------|--------|
| "결론적으로", "중요한 건", "제가 하고 싶은 말은" 뒤에 온다 | 높음 |
| 세미나 안에서 2회 이상 반복된다 | 높음 |
| Q&A에서 다시 나온다 (청중이 그걸 물었다는 뜻) | 높음 |
| 근거·데이터·사례가 붙어 있다 | 중간 |
| 길게 말했지만 반복도 강조 표지도 없다 | 낮음 — 곁가지일 가능성 |
| 다른 사람의 말을 인용한 것 | claim 아님. `quotes`에 화자를 제3자로 |

`weight`는 1(핵심)~3(부수). 카드뉴스와 덱은 weight 1만 쓰고, 요약은 2까지, 인포그래픽은
전체 구조를 보여주므로 3까지 쓴다. **뒤 단계의 분량 조절이 이 필드에 걸려 있으니 성의껏 매겨라.**

## 3. 인용(quotes) 규칙

- **전사본에서 글자 그대로.** 다듬으면 인용이 아니라 창작이다
- 말버릇·중복 제거는 `[…]`로 생략 표시: `"이게 결국 […] 신뢰의 문제예요"`
- 3~7개. 그 이상은 인용이 아니라 발췌록이다
- 고르는 기준: **요약으로 대체할 수 없는 것**. 요약해도 뜻이 안 죽는 문장은 인용할 이유가 없다

## 4. 수치(numbers) 규칙

숫자만 맞고 단위·기준이 틀린 것이 가장 흔한 사고다. `basis`를 반드시 채운다:
`"2024년 대비"`, `"자사 내부 측정 n=80"`, `"발표자 추정치"`. 발표자가 기준을 말하지
않았으면 `basis: "발표자가 기준을 명시하지 않음"`이라고 적는다 — 이 문장이 뒤 단계에서
차트로 그리면 안 되는 숫자를 걸러낸다.

## 5. 세미나 특유의 함정

| 함정 | 대응 |
|------|------|
| 여는 인사·자기소개를 내용으로 착각 | `sections`에 넣되 `claims`는 뽑지 않는다 |
| Q&A를 버림 | Q&A는 **청중이 실제로 궁금해한 것**이다. `qna`에 남긴다 — 카드뉴스 소재로 가장 잘 쓰인다 |
| 여러 발표자를 한 논지로 뭉갬 | `sections`를 발표자 단위로 나누고 `speakers`를 채운다 |
| 발표자의 농담·반어를 주장으로 채택 | 앞뒤 문맥을 본다. 애매하면 `uncertain`으로 |
| 발표자가 인용한 남의 주장을 발표자 주장으로 귀속 | `quotes.speaker`를 제3자로. 이건 팩트체크가 잡는 3대 항목 중 하나다 |
| 슬라이드를 읽는 구간 | 전사본만으로는 화면이 안 보인다. 지시대명사("이 그래프에서 보시면")가 나오면 `uncertain`에 남긴다 |

## 6. 팩트체크 판정 기준

검증자는 **고치지 않는다.** 판정만 하고 수정은 분석 담당이 한다. 자기가 쓴 걸 자기가
통과시키면 게이트가 아니다.

세 가지만 본다. 문체 취향은 issue가 아니다.

| kind | 무엇 | 판정 방법 |
|------|------|----------|
| `hallucination` | 전사본에 없는 사실 | 각 claim의 `at` 구간을 열어 실제로 그 말이 있는지 |
| `misquote` | 인용문 불일치 | **`Grep`으로 문자열 대조.** "비슷하니 맞겠지"는 판정이 아니다 |
| `misattribution` | 화자 귀속 오류 | 그 구간의 화자가 맞는지, 제3자 인용이 아닌지 |
| `number` | 단위·기준 오류 | 값·단위·`basis`를 전사본과 대조 |
| `note` | 애매한 경계 | 통과시키되 기록 (예: 발표자가 인용한 제3자 발언) |

**`pass`는 `hallucination`·`misquote`·`misattribution`·`number`가 0건일 때만 true.**
`note`는 pass를 막지 않는다.

반환 형식:
```json
{ "pass": false,
  "issues": [{ "path": "claims[2]", "kind": "hallucination",
               "detail": "00:07:31 구간에 해당 주장 없음. 유사한 말은 00:09:02의 '…'이나 뜻이 다름" }] }
```

`detail`에는 **무엇이 틀렸는지와 근거 위치**를 쓴다. "확인 필요"는 판정이 아니다.
