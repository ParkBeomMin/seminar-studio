# 산출물 4종 규격

입력은 항상 `_workspace/02_core.json` 하나. **담당 format의 절만 읽어라** — 4종 전부 읽을 필요 없다.

**하나의 녹음에 세션이 여럿이면 세션마다 4종을 따로 만든다.** 입력으로 받는 `part`가 그
단위이며, 산출물은 `output/{part.id}/` 아래로 간다. 다른 발표자의 다른 주제를 한 장의
카드뉴스나 한 벌의 덱에 섞으면 둘 다 초점을 잃는다. `part`가 지정되면 **그 파트의
sectionIds에 속한 claims·quotes·numbers·qna만 쓴다** — 다른 파트의 내용을 끌어오지 마라.

원칙 하나: 매체가 다르면 구성이 달라야 한다. 코어를 그대로 붓는 것이 이 일의 실패다.
그리고 **코어에 없는 사실을 추가하지 않는다.** 허전해 보이는 곳은 채우는 게 아니라 줄여서 해결한다.

## 0. 공통 비주얼 시스템 — 4종이 공유한다

4종이 따로 놀면 같은 세미나의 산출물로 안 보인다. 아래 토큰을 임의로 바꾸지 마라.

```css
:root{
  --ink:#16181d; --ink-2:#4a4f5a; --line:#e2e5ea;
  --bg:#fbfbfc; --surface:#fff; --accent:#2f6df6; --accent-soft:#eaf0fe;
  --radius:14px; --gap:24px;
  --font:"Pretendard","Apple SD Gothic Neo",-apple-system,system-ui,sans-serif;
}
```

- 강조색은 **`--accent` 하나만.** 두 번째 색을 쓰고 싶으면 그건 대개 정보 위계가 안 잡힌 것이다
- 한국어 본문은 `line-height:1.7`, `word-break:keep-all` (단어 중간 줄바꿈 방지 — 안 넣으면 카드뉴스가 무너진다)
- 다크 모드: HTML 산출물은 `:root:not([data-theme="light"])` 아래 `prefers-color-scheme: dark` 블록으로 토큰만 재정의한다

## 0-1. 산출물은 녹음에서 나왔다는 티를 내지 않는다

**독자가 읽는 것은 내용이지 녹음의 기록이 아니다.** 코어(`02_core.json`)는 타임코드와 근거를
전부 들고 있지만 그건 **내부 검증용**이다. 산출물에는 그 배관이 보이면 안 된다.

| 넣지 않는다 | 대신 |
|---|---|
| 타임코드 (`00:12:01`), 구간 표기, 녹음 길이 | 아무것도. 지우면 된다 |
| "발표자는 ~라고 말했다", "이번 세미나에서는" | 내용을 직접 서술한다 — "기록은 사람이 매일 공급해야 한다" |
| "1부 발표", "2부 패널", 세션 구조 | 파트의 `title`을 그 글의 제목으로 쓴다 |
| 전사 결손·STT 오인식 고지 | 아무것도. 해당 내용을 빼면 된다 |
| `confidence`·`uncertain` 자체를 독자에게 노출 | 아래 규칙대로 **빼거나 완화**한다 |

**약한 항목은 경고를 붙이는 게 아니라 뺀다.** 이전 판에서는 기준 없는 수치에
"그대로 인용하기 전 원문 확인 필요"를 달았는데, 그 문장 자체가 녹음 기록의 냄새다.
자립적인 글에서는 근거가 약하면 **싣지 않는 것**이 정직하다:

- `basis`가 미명시·자기진술인 수치 → **싣지 않는다.** 꼭 필요하면 숫자를 빼고 방향만 쓴다 ("도입 후 주가가 올랐다")
- `uncertain`에 걸린 제품명·인명 → 고유명사를 빼고 기능으로 쓴다 ("회의록 서비스")
- 발표자가 스스로 단서를 단 주장("이론적으로는") → 그 단서를 문장에 녹여 쓰거나 뺀다

**남기는 것:** 아이디어의 원 출처 귀속은 녹음 흔적이 아니라 정상적인 인용이다.
노션 지사장의 장표, 잭 도시의 말, Y컴비네이터의 문구는 누구 것인지 밝혀 쓴다.
말한 사람의 이름도 남긴다 — 남의 생각을 출처 없이 제 것처럼 쓰는 게 더 나쁘다.

## 1. `summary` → `output/<part>/summary.md`

읽는 순서 그대로. 스캔이 아니라 통독 대상이다.

```markdown
# {title}
> {thesis}

## 한눈에
- {takeaway 3~5개}

## 논지
### {section.title}
{gist를 풀어쓴 3~5문장. claims weight 1~2를 근거와 함께}
> {quote} — {speaker}

## 숫자
| 지표 | 값 | 무엇을 잰 것인가 |
|---|---|---|
{기준이 분명한 것만. 미명시 수치는 표에서 뺀다}

## 자주 나오는 질문
**Q.** … **A.** …

## 열린 질문
{이 주제에서 아직 답이 없는 것}
```

- 분량 A4 2~3장. 소스가 길다고 비례해 늘리지 마라 — 요약의 가치는 버린 양에 있다
- **"열린 질문"을 생략하지 마라.** 다뤄지지 않은 것을 아는 게 다뤄진 것을 아는 만큼 쓸모 있다.
  단, 여기 적는 것은 **주제상 답이 안 나온 물음**이지 소스의 결함이 아니다

## 2. `cardnews` → `output/<part>/cardnews.html`

SNS 카드뉴스. **한 장에 한 생각.** 두 생각이 들어가면 둘 다 안 읽힌다.

| 항목 | 규격 |
|------|------|
| 장수 | 8~10장 (표지 1 + 본문 6~8 + 마무리 1) |
| 아트보드 | **1080×1350 실제 크기** (4:5). 인스타 피드에서 세로를 가장 많이 먹는 비율 |
| 헤드라인 | 15자 내외, **54~72px** (아트보드가 1080px 폭이다 — 34px는 폭의 3%라 피드에서 안 읽힌다) |
| 본문 | **90~160자**, 32~36px. 아래 "여백" 참조 |
| 캡션 | 24~27px |
| 소스 | `claims` weight 1 + `qna` (Q&A가 카드뉴스 소재로 가장 잘 먹는다 — 청중이 실제로 궁금해한 것이니까) |

구성: 표지(제목+thesis) → 문제 제기 → 핵심 주장 3~5장 → 인용 1장 → 마무리(takeaways)

### 축소 미리보기 — 반드시 이 패턴으로

카드는 **1080px 원본 크기로 존재**하고 화면에서만 축소해 보여준다. 캡처하면 원본 해상도가 나와야 하기 때문이다. 축소는 `transform:scale()`로 하는데 **여기에 함정이 하나 있다:**

```css
/* 틀림 — transform이 통째로 무시된다 */
:root{ --cw:540px; }
.card{ transform:scale(calc(var(--cw) / 1080)); }   /* calc(540px/1080) = 0.5px */

/* 맞음 — 스케일 변수는 무단위여야 한다 */
:root{ --cw:540; }
.frame{ width:calc(var(--cw) * 1px); height:calc(var(--cw) * 1.25px); overflow:hidden; }
.card { width:1080px; height:1350px; transform:scale(calc(var(--cw) / 1080)); transform-origin:top left; }
```

`scale()`은 **무단위 수**를 받는다. 길이가 들어가면 CSS가 선언 전체를 버리고, 카드는 축소되지 않은 채 1080px로 렌더돼 `overflow:hidden` 프레임에 **오른쪽과 아래가 잘린다.** 에러도 경고도 안 난다. 이 하네스에서 실제로 난 사고이며, 내용량 점검으로는 절대 안 잡힌다.

`.card`에 `aspect-ratio`를 같이 걸지 마라 — 높이 계산을 가로채서 검사 도구가 자연 높이를 못 잰다.

### 검증 게이트 — 건너뛰지 마라

```bash
node .claude/skills/seminar-deliverables/scripts/check_cards.mjs output/<part>/cardnews.html --sel .card
```

두 가지를 잰다: ① 내용이 1350px에 들어가는가 ② 렌더 결과가 프레임 밖으로 잘리는가.
**exit 0이 아니면 산출물을 완성으로 보고하지 마라.**

- `+Npx 넘침` → **글을 줄여라.** 폰트를 줄이면 다음 카드와 위계가 깨진다
- `렌더 클리핑` → 위의 `scale()` 함정이다. 글 양은 손대지 마라

### 여백

카드는 꽉 차 보일 필요가 없다 — 여백이 SNS에서 읽히게 만든다. 다만 본문이 두 줄뿐이면
1350px 중 절반이 빈다. 그 경우 근거(`support`)를 캡션으로 붙여 밀도를 올려라 — 주장만 있고
근거가 없는 카드가 가장 안 읽힌다. 코어에 없는 문장을 지어내 채우는 것이 최악이다.

## 3. `infographic` → `output/<part>/infographic.html`

**요약의 내용을 그림으로 만드는 것이다.** 강의의 구조를 그리는 것이 아니다.

이 자리에서 실제로 났던 실패: 섹션 13개를 시간 비율 리본으로 그리고 구간 목록을 2단으로
깔고 claims 28건을 전부 나열했다. 그건 **목차이지 인포그래픽이 아니다.** 세미나가 어떻게
진행됐는지는 아무도 안 궁금하다. 세미나가 **무슨 말을 했는지**가 궁금한 것이다.

| | 넣는다 | 넣지 않는다 |
|---|---|---|
| 소스 | `thesis`, `takeaways`, `claims` weight 1 | claims 전량, `sections` 목록 |
| 축 | **개념의 구조** — 무엇이 무엇으로 이어지는가, 무엇이 무엇과 대비되는가 | 시간축, 발표 순서 |
| 금지 | — | 구간 타임라인 리본, 목차 블록, "1부/2부" 진행 구조 |

| 항목 | 규격 |
|------|------|
| 크기 | 폭 1200px, 세로 2400~3600px |
| 차트 | `numbers`가 **같은 축에 올릴 수 있을 때만.** 단위가 제각각이면 큰 숫자 타일로 |

### 구성 — 이 순서로 짠다

1. **헤더** — 제목 + thesis 한 문장. 이 한 문장이 인포그래픽 전체의 주제다
2. **핵심 대비 또는 모델 다이어그램** — 이 세미나의 중심 아이디어를 그림 하나로.
   대비형(A가 아니라 B다), 단계형(A→B→C), 구조형(중심과 그 주변) 중 하나를 고른다
3. **takeaway별 블록** — 각 takeaway를 제목으로, 근거 claim을 본문으로. 3~5개
4. **수치** — 큰 숫자 타일
5. **인용 배너** 1~2건
6. **푸터** — 제목과 출처(누가 한 이야기인지) 한 줄. 그 이상 넣지 마라

### 다이어그램

2번이 이 산출물의 중심이다. **`artifact-diagramming` 스킬을 읽고 그려라** (없으면: 진짜 관계를
보여라 — 상자를 화살표로 잇기만 한 그림은 아무것도 설명하지 않는다). 이 세미나에서 그릴 만한 것의 예:
`코파일럿(도구) ↔ 사고 파트너(팀원)` 대비, `기록 → SOP 자동 갱신 → 거버넌스` 단계.

차트를 만들 때는 `dataviz` 스킬을 먼저 읽는다.
`basis`가 `"발표자가 기준을 명시하지 않음"`인 수치는 **차트로 그리지 마라** — 큰 숫자 타일로
두고 캡션에 그 사실을 적는다. 기준 없는 숫자를 막대로 그리면 없는 정확도가 생긴다.

## 4. `deck` → `output/<part>/deck.pptx`

진짜 .pptx 파일. 빌드는 번들 스크립트로:

```bash
.venv/bin/python .claude/skills/seminar-deliverables/scripts/build_pptx.py \
  --spec _workspace/<part>_deck_spec.json --out output/<part>/deck.pptx
```

`_workspace/<part>_deck_spec.json`을 먼저 쓴다. 스키마는 `scripts/build_pptx.py` 상단 주석 참조.

| 항목 | 규격 |
|------|------|
| 장수 | 12~18장 (표지 1 + 목차 1 + 본문 9~14 + 마무리 1) |
| 비율 | 16:9 (13.33 × 7.5 인치) |
| 슬라이드당 | **한 메시지.** 제목이 그 메시지의 문장이 되게 쓴다 ("도입 현황"이 아니라 "도입은 늘었지만 정착은 안 됐다") |
| 불릿 | 최대 4개, 각 20자 내외. 문장을 통째로 넣지 마라 |
| 소스 | `sections`를 슬라이드 그룹으로, `claims` weight 1~2를 본문으로 |

- **폰트를 바꿀 때는 `<a:ea>`까지 바꿔야 한다.** python-pptx의 `run.font.name`은 `<a:latin>`만
  설정하고, 한글은 `<a:ea>`(East Asian) 타이프페이스를 따른다. 이걸 놓치면 라틴 문자만 지정
  폰트로 나오고 **한글은 테마 기본 명조로 폴백해** 덱이 딴판이 된다. 번들 빌더의 `_font()`가
  latin·ea·cs 셋을 함께 박으니 그걸 거쳐 쓴다. 폰트 이름은 `DECK_FONT` 환경변수로 바꾼다
  (기본값 `Apple SD Gothic Neo` — 설치돼 있지 않은 기기가 많은 이름을 기본값으로 두면 안 된다)
- 발표자 노트(`notes`)에는 **그 슬라이드에서 말할 내용**을 넣는다. 근거·맥락·예시를 문장으로.
  타임코드나 코어의 id(`c12` 등)를 노트에 남기지 마라 — 그것도 배관이다
- python-pptx 실패 시 **에러 원문을 그대로 보고한다.** 빈 pptx를 만들어 성공으로 보고하지 않는다

## 5. 4종 공통 체크

- [ ] 코어에 없는 사실이 들어가지 않았나
- [ ] **타임코드·구간·"발표자가 말했다"·전사 결손 고지가 한 군데도 남지 않았나** (§0-1)
- [ ] 근거가 약한 수치·고유명사를 경고와 함께 싣지 않고 **뺐나** (§0-1)
- [ ] 남의 아이디어를 출처 없이 쓰지 않았나 (귀속은 남긴다)
- [ ] 4종의 용어가 일치하나 (같은 개념을 카드뉴스는 A, 덱은 B로 부르면 안 된다)
- [ ] 인용문이 코어의 `quotes.text`와 글자 그대로 일치하나
